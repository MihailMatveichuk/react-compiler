# React Compiler

Демо-проект про то, как React решает, что перерисовать заново, а что достать из кеша: `React.memo`, `useMemo`, `useCallback`, и как всё это сегодня умеет писать за вас React Compiler.

Проект запускается как обычный Vite + React приложение:

```bash
npm install
npm run dev
```

React Compiler включён через `oxc-transform-react` в `vite.config.js` (см. закомментированный параметр рядом с ним — аналогичную активацию Babel-версии через `babel-plugin-react-compiler`, если хочется переключиться на неё и сравнить вывод).

## Проблема: лишние перерисовки

```jsx
const [clicks, setClicks] = useState(0);

return (
    <div>
        <button onClick={() => setClicks((c) => c + 1)}>Рендерим родителя</button>
        <HeavyChild items={items} />
    </div>
);
```

**Что происходит.** У родителя меняется только `clicks`. По идее, ребёнка это не касается: у него те же `items`. Но на каждый ре‑рендер родителя React вызывает рендер и у `HeavyChild` тоже — потому что JSX пересобирается, а компонент по умолчанию перерисовывается всегда.

**Как смотреть.** В каждом демо есть `RenderBadge` — счётчик реальных рендеров. Кнопка «Рендерим родителя» прибавляет к `clicks`. Смотрим на два счётчика. Если счётчик ребёнка стоит, а счётчик родителя растёт — мемоизация сработала. Если растут оба — вы смотрите на «чистый» React без оптимизаций.

## `React.memo`

Обёртка над целым компонентом. Сравнивает прошлые и новые пропсы. Если поверхностно всё равно — не рендерит с нуля, а отдаёт прошлое дерево.

```jsx
const MemoHeavyChild = memo(function MemoHeavyChild({ items }) {
    return <HeavyList items={items} />;
});
```

**Что происходит.** Перед каждым ре‑рендером React проверяет: те ли пришли `items`, что и в прошлый раз? Если да — рендер `MemoHeavyChild` пропускается вообще.

**Когда полезно.** Ребёнок дорогой по рендеру, а родитель часто меняет своё состояние, не имеющее к нему отношения: вкладки, счётчики, поисковую строку.

**Когда бесполезно.** Пропсы меняются постоянно. Тогда сравнение просто даром пробегает, а ребёнок перерисовывается как и раньше.

**Где живёт сквозная мысль.** `React.memo` сравнивает пропсы поверхностно. Если в пропсах лежит объект или массив, родитель создал ими новый объект прямо в теле рендера — ссылка новая, сравнение падает, ребёнок рендерится заново. Дальше идём за `useMemo`.

## `useMemo`

Мемоизирует **значение**, а не компонент. Функция внутри пересчитывается тогда, когда изменилось что‑то из зависимостей.

```jsx
const shown = useMemo(() => items.filter(item => item.label.includes(query)), [items, query]);
```

**Что происходит.** Первый рендер — вычисляем функцию и кладём результат в кеш. Дальше смотрим: не изменился ли `items` или `query`? Если те же — возвращаем `shown` с прежней ссылкой. Новый рендер не вызывает фильтрацию заново.

**Где реально нужно.**

- Значение уходит в `React.memo`‑ребёнка: тот проверяет ссылку. Без `useMemo` всегда получите новый массив, и `React.memo` никогда не сработает.
- Дорогое вычисление: сортировка, фильтрация, агрегация списка, парсинг.

**Когда бесполезно.** Дешёвое вычисление: `str.length`, небольшая склейка строк, пара замен/парсов. Пересчитать такое всегда дешевле, чем платить поддержкой ради читаемости. И главное: `useMemo` **не** отменяет ре‑рендер самого компонента — он лишь сохраняет ссылку на результат вычисления.

**Всегда помним.** Зависимости указываем только те, от которых на самом деле зависит вычисление. Если завязаться на всё, получим прежний пересчёт; если указать «липовую» зависимость, которую мы сами мутируем внутри, — сломаем синхронизацию.

## `useCallback`

Мемоизирует **функцию** по схожей схеме. Только вместо значения кладёт в кеш ссылку на обработчик.

```jsx
const handleSelect = useCallback(id => setSelected(id), []);
```

**Что происходит.** Пока зависимости не изменились, возвращается та же самая ссылка на функцию. У `memo`‑ребёнка это означает «новой функции нет, пере‑рендер не нужен».

**Когда нужно.** Только когда функция идёт в пропсы:

- в `React.memo`‑ребёнка — иначе новый обработчик ломает сравнение и сводит к нулю весь смысл `React.memo`;
- в зависимости `useEffect`, таймера, слушателя, субскрипшена;
- в библиотеку, рассчитывающую на стабильность ссылки (`Apollo`, `Formik`, виртуализаторы списков).

**Где обычно ошибаются.** Думают, что `useCallback` сам по себе уменьшает число рендеров. Он этого не делает. Он лишь держит стабильную ссылку на функцию, чтобы ничего внутри сверяющего эту ссылку (например `React.memo` или `useEffect`) не пересчитывалось зря.

## Когда мемоизация не нужна

Мемоизация — это настройка на «а быстрее». Если применять её как привычку, вместо выигрыша получаем дурацкий код и тонну багов.

- **Короткий список.** `React.memo` на списке из трёх строк, которые рендерятся за 10 мс. Добавляем сложности, выигрываем 0,1 мс.
- **Быстрое вычисление.** `useMemo` на `list.length`, на расширение строки, на конкатенацию `a + b` — это всегда пересчитать быстрее, чем кешировать.
- **Зависимость всегда новая.** Если зависимость мы каждый рендер создаём сами, `useMemo` не сработает никогда: сравнение всегда «новый».
- **Мутабельные объекты.** Мемоизация работает только для иммутабельных данных. Если мутировать массив на месте, сравнение промахнётся и кеш отдаст не под новые данные.

Правило простое: **не мемоизируйте всё подряд — снимайте замеры.** Надёжный способ — React DevTools Profiler: там видно, кто и на каком рендере потратил время больше всех.

## React Compiler

До сих пор мы расставляли `React.memo`, `useMemo`, `useCallback` руками. Compiler умеет проставлять их за вас. В этом уроке есть готовый `CompilerDemo`: два одинаковых списка, у одного мемоизацию делает Compiler, у второго —`"use no memo"` — Compiler говорит им не трогать, чтобы показать разницу.

В этом проекте подключены оба способа — активен Rust-вариант, Babel-путь лежит закомментированным в `vite.config.js`. Оба отдают Vite одно и то же: мемоизацию компонентов.

**Вариант 1 (активен) — `oxc-transform-react`.** Rust-порт React Compiler'а от команды oxc. Это новый дефолт для Vite 8: `react({ compiler: true })` сам подхватывает пакет.

```js
// vite.config.js
import react from "@vitejs/plugin-react";

plugins: [
    react({ compiler: true }), // тянет oxc-transform-react из optional peer deps
    tailwindcss(),
];
```

Установка: `npm i -D oxc-transform-react`. Ключ `compiler` принимает не только `true`, но и опции самого компилятора, например `react({ compiler: { compilationMode: 'annotation' } })` — тогда обрабатываются только компоненты с директивой `"use memo"`. Поддерживается и `logDiagnostics: true` — показывает диагностику компилятора прямо в терминале Vite. Быстрый, но помечен как experimental — официальная документация React Compiler для этого пути ещё догоняет Babel-ссылку с react.dev.

**Вариант 2 — `babel-plugin-react-compiler`.** Тот самый скрипт сборки, описанный в [react.dev/learn/react-compiler](https://react.dev/learn/react-compiler). В Vite 8 он подключается через отдельный роут — хелпер `reactCompilerPreset()` и `@rolldown/plugin-babel`:

```js
// vite.config.js — активный вариант меняем на этот
import react, { reactCompilerPreset } from "@vitejs/plugin-react";
import babel from "@rolldown/plugin-babel";

plugins: [
    react(), // без compiler: true
    babel({ presets: [reactCompilerPreset()] }),
    tailwindcss(),
];
```

Установка: `npm i -D @rolldown/plugin-babel @babel/core babel-plugin-react-compiler`. У `reactCompilerPreset()` те же опции — `compilationMode`, а для React 17/18 предусмотрен `target: '17'` или `'18'` (подтянет `react-compiler-runtime` вместо `react/compiler-runtime`). Медленнее, но проверен временем и совпадает с докой.

**Как обычно включать.** В `vite.config.js` рядом с каждым вариантом уже написано, какой пакет что тянет. Активен вариант 1, вариант 2 закомментирован прямо рядом — чтобы найти их в собранном бандле и сравнить разницу, раскомментируй один и закомментируй другой.

**Что делает Compiler.** Он запускается на этапе сборки, обходит компоненты в дереве и вставляет `React.memo`, `useMemo`, `useCallback` ровно там, где это выигрывает время. Явно по файлу в собранном бандле видно кеш-сравнение `t[0] === Symbol.for("react.memo_cache_sentinel")` — это тело внутренней функции Compiler'а.

**`"use no memo"` — это не «запретить мемоизацию».** Это «этот компонент Compiler никогда не трогай». Пригодится трём сценариям:

- легаси‑код, который проще читать и дебажить без преобразований;
- дебаг, когда важно видеть, как компонент ведёт себя без авто‑мемоизации;
- случаи, когда хуки держат вручную на каждом рендере, и авто‑мемоизация была бы лишней.

**Важное уточнение.** Существующие рукописные `useMemo`/`useCallback` Compiler не удаляет — он пытается дать им те же гарантии. Если компонент нужно оставить в исходном виде неоптимизированным, ставим `"use no memo"` — это отключает авто‑реврай для конкретного компонента, без влияния на остальное дерево.

### Важные опции Compiler'а

По умолчанию компилятор работает с инфером (`infer`) и React 19, трогая всё, кроме `node_modules`. Ниже — те опции, до которых обычно доходят руками. Оба варианта подключения (Babel и Rust) принимают одну и ту же пару директив и почти одни и те же ключи.

#### `compilationMode` — что вообще трогать

```js
react({ compiler: { compilationMode: "infer" } }); // по умолчанию
```

- **`infer`** — автоопределение: сам решает по коду, где это компонент/хук, где просто функция. Тот режим, с которым вы работаете 99% времени.
- **`syntax`** — компилировать любую функцию с `"use memo"`, даже если она не React-компонент.
- **`annotation`** — **только** функции с директивой `"use memo"`; всё остальное трогать нельзя. Самый «безопасный» режим для внедрения в большой проект.
- **`all`** — всё, включая файлы без React. Практически не нужен.

#### `target` — под какую версию React

```js
react({ compiler: { target: "19" } }); // по умолчанию
react({ compiler: { target: "17" } }); // или "18"
```

Это не версия JSX-трансформа, а то, **куда** компилятор кладёт хелпер мемоизации. Для `"19"` генерится `import 'react/compiler-runtime'` (приходит вместе с React). Для `"17"`/`"18"` — `react-compiler-runtime`, это отдельный пакет, который нужно доставить в проект руками. Если в `package.json` старый React, а опция осталась в дефолте — после сборки получите ошибку рантайма.

#### `sources` — фильтр по именам файлов

```js
// Babel-вариант: массив строк ИЛИ функция-фильтр
babel({
    presets: [reactCompilerPreset({
        sources: ["src/Memoization", "src/Forms"], // подстроки в пути файла
        // или: sources: (filename) => !filename.includes("src/legacy"),
    })],
});

// Rust-вариант: только массив строк (уникальная оговорка)
react({ compiler: { sources: ["src/Memoization"] } });
```

- **Babel** принимает либо массив строк, либо **функцию-фильтр** `(filename) => boolean` — самое гибкое.
- **oxc** принимает только массив строк: функция фильтр не сериализуется через нативный биндинг. Правило простое — файл трогается, если содержит хотя бы одну из подстрок.
- Передача своего `sources` **полностью заменяет** дефолтный фильтр по `node_modules`, а не дополняет его.

#### `panicThreshold` — как реагировать на ошибки

```js
react({ compiler: { panicThreshold: "critical_errors" } }); // или "none", "all_errors"
```

Что делать, если Compiler считает код неподдающимся компиляции. `"none"` (дефолт) — пропустить файл и идти дальше; `"critical_errors"` — прерваться только на фатных; `"all_errors"` — прерваться на любой. Для CI-прогона логично `"critical_errors"`, чтобы случайно неработающий кусок остался незамеченным.

#### Как выйти из-под компиляции, кроме `"use no memo"`

- **`customOptOutDirectives: ["use legacy render"]`** — объявить свою директиву-«выключатель» наравне с `"use no memo"`.
- **`eslintSuppressionRules`** — какие именно комментарии `eslint-disable-next-line` / `oxlint-disable-next-line` тоже считать отключением компиляции. По умолчанию там два правила хуков.
- **`ignoreUseNoForget: true`** (только oxc) — наоборот, компилировать даже `"use no memo"`. Полезно, чтобы проверить «а что было бы с этим куском, если бы мемоизацию не запретили».

#### Диагностика и режим только-без-генерации

Опция `compiler` умеет не только генерить, но и просто проверять код. Через oxc это `reportDiagnostics: true`, оно складывается в `result.errors`; у Vite-плагина поверх этой опции стоит `logDiagnostics: true`, которое репортит прямо в терминал Vite. Альтернатива — `outputMode: "lint"` или старый флаг `noEmit`: остаются только диагностики Compiler'а, без переписывания кода. Удобно включить на CI как отдельный шаг, чтобы ловить «Compiler не понял этот кусок» до того, как вы узнаете о проблеме через имбаунд.

#### Редкие, но интересные environment-опции

Почти всё живёт в объекте `environment` и по умолчанию включено разумное. Чаще всего руками трогают именно это поле:

```js
react({
    compiler: {
        environment: {
            enablePreserveExistingMemoizationGuarantees: true,   // читать ваш ручной useMemo/useCallback
            validatePreserveExistingMemoizationGuarantees: true, // проверить, что Compiler их не сломал
            validateExhaustiveMemoizationDependencies: true,      // проверять полноту зависимостей у useMemo/useCallback
            enableNameAnonymousFunctions: true,                   // давать имена анонимным функциям — удобно в трассировках
        },
    },
});
```

#### `enablePreserveExistingMemoizationGuarantees`

Это источник утверждения «Compiler не удаляет ваши ручные `useMemo`/`useCallback`». Флаг заставляет компилятор **учитывать** при работе эти уже написанные вами мемоизации: не считать их просто «новым вычислением», которое можно переписать, а сохранять referential-equality, на которую рассчитан остальной код (например, объект, уходящий в зависимости эффекта, или обработчик, сравнивающийся по ссылке в `React.memo`-ребёнке).

```js
// /tmp/memocheck/in2.jsx — тот случай, где ссылочная стабильность ломает useEffect
function Parent({ id }) {
    const [n, setN] = useState(0);
    const style = useMemo(() => ({ color: n > 0 ? "red" : "blue" }), [n]);
    const handle = useCallback((x) => console.log(id, x), [id]);
    useEffect(() => {
        schedule(handle, style);
    }, [handle, style]);
    return <Child onPick={handle} />;
}
```

С инпендементальным тестом эта и похожие кусочки дают у oxc **одинаковый вход** при `enablePreserveExistingMemoizationGuarantees: true` и `false` — Compiler оптимизирует идентично, а эффект так и так встряхивает справа только когда `handle`/`style` меняются по существу. Что флаг реально даёт, видно на краевых случаях, где ссылочная стабильность была единственной гарантией (глобальный identity, context-value, селектор в внешнем сторе). Сама формулировка из документации обещает ровно это: *"use information from useMemo/useCallback to preserve referential-equality behavior"*. Проверить на своём куске кода можно, скормив oxc два варианта конфига побайтно и сравнив на выходе.

#### Debug: как увидеть, что Compiler ломает ручную мемоизацию

Рядом есть компаньон-флаг `validatePreserveExistingMemoizationGuarantees` (по умолчанию `true`). Он включает обратную проверку: Compiler сам прогоняет, что его переписывание сохранило ваши referential-equality гарантии. Сборка при `reportDiagnostics`/`logDiagnostics` покажет предупреждение, если сломала.

```js
// vite.config.js — честная проверка при разработке
react({
    compiler: {
        logDiagnostics: true,
        environment: {
            enablePreserveExistingMemoizationGuarantees: false, // специально ломаем
            validatePreserveExistingMemoizationGuarantees: true, // и ловим себя
        },
    },
}),
```

Порядок дебага такой:

1. Берём кусок кода с ручным `useMemo`/`useCallback`, ищем место, где его результат идёт дальше по ссылке — в зависимости, в пропсы`React.memo`-ребёнка, в `useEffect`.
2. Включаем `logDiagnostics: true` от `oxc`/`reactCompilerPreset` и намерено отключаем `enablePreserveExistingMemoizationGuarantees`.
3. Смотрим, не ругается ли Compiler. Если ругнулся с включённой валидацией — это признак, что гарантия ваших ручных хуков в этом месте реально важна, и её стоит зафиксировать тестом на referential equality.
4. Если нужен и в проде «Ломай меня, но предупреждай» — оставьте оба флага как выше, но не репортите в терминал, а сложите диагностики в CI и фейльтесь по ним.

Остальные `validate*` включают отдельные проверки Compiler'а: использование хуков через ифы, доступ к `ref` во время рендера, `setState` в рендере и в эффектах. Это правило «Compiler тоже линтует» — выключайте только если вам нужен старый легаси-код без правок.

### Compiler и Context

Compiler работает с `useContext`, но делает это **иногда лучше, чем руками написанный `useMemo`**. Причина в том, что акцент Compiler'а — на реактивность значения, а не на пользователя конкретного `useMemo`. Каждый доступ к полю контекста становится отдельной отслеживаемой зависимостью, и пересчёт идёт только для той ветки кода, где значение реально поменялось.

Проверим на примере с компонентом, который одновременно использует и тему, и счётчик из одного и того же Context:

```jsx
function ThemePanel() {
    const { mode, upaCount } = useContext(ThemeContext);
    return (
        <div>
            <Badge mode={mode} />
            <Counter n={upaCount} />
        </div>
    );
}
```

Скомпилированный вывод (oxc):

```js
function ThemePanel() {
    const $ = _c(7);
```

Каждая ветка (Badge, Counter) мемоизируется **отдельно**, и пересчёт зависит только от тех полей, которые реально меняются: клик в Counter не трогает Badge и наоборот. У `useMemo` такого уровня детализации не было бы — он держал бы только одну ссылку на props целиком.

**Что Compiler не может.** Он видит только сам файл — Provider и Consumer могут жить в разных файлах. Он не знает, «сколько раз `AuthProvider` действительно менял значение». За отсечение лишних ререндеров на уровне Provider→Consumer отвечает сам React: Consumer перерисовывается только когда значение, которое отдаёт Provider, поменялось по `Object.is`. Compiler'у остаётся — не зря пересчитывать производные внутри того компонента, который контекст использует. Он делает именно это.

**`lowerContextAccess` — опция environment для точечной оптимизации.** По умолчанию выключена. Позволяет Compiler'у переписывать доступы вида `ctx.user.profile.avatar` в более тонкий плоский доступ к полю, сводя к минимуму следы от неважных полей контекста:

```js
react({
    compiler: {
        environment: {
            lowerContextAccess: { source: 'react', importSpecifierName: 'useContext' },
        },
    },
});
```

Источник и имя хука задают, какой именно гук считается «доступом к Context». Практический эффект — в дочерних компонентах, получающих большие объекты контекста как пропсы и вычисляющих из поля узкую зависимость, заметно реже будут пересчитываться производные из-за обновлений ненужных полей. В тривиальном демо разница может быть невидима глазу — она проявляется при общем большом объекте контекста с несколькими группами поля, которые вызываются в разных ветках UI.

**Правило урока для студентов.** Контекст у Compiler — полноценный реактивный источник. Не расстраивайтай, если `useMemo` на «своей половине контекста» выглядит громоздко: Compiler сделает работу за вас и разделит пересчёт на поля. Ручной `useMemo` с одним большим объектом из контекста, наоборот, будет пересчитываться шире — это тот случай, когда Compiler честно выигрывает у ручной мемоизации.

---

**`"use no memo"` работает в обоих вариантах подключения.** Разницы нет никакой: это опция самого компилятора, а не свойство конкретного пакета. `babel-plugin-react-compiler` физически принимает обе директивы — современное `"use no memo"` и старое, до ребрендинга, `"use no forget"`.

```js
// так компилятор решает, трогать ли функцию
var OPT_OUT_DIRECTIVES = new Set(["use no forget", "use no memo"]);
```

Rust-порт `oxc-transform-react` держит тот же алгоритм и ту же пару директив, а расширение есть только одно — опция `ignoreUseNoForget`, по умолчанию выключенная. То есть, переключаясь между Rust- и Babel-вариантом в `vite.config.js`, код не меняем: директивы выше остаются такими же, и `"use no memo"` гарантирует одно и то же поведение.

### Как смотреть мемоизацию в React DevTools

Чтобы увидеть разницу между «написал руками» и «проставил Compiler», открываем React DevTools (вкладки **Components** для дерева и **Profiler** для замеров рендеров).

- **`Memo(Имя)`** — компонент, обёрнутый в `React.memo` вами самими, например демо с `WithMemo`. DevTools просто показывает имя обёртки: `Memo(MemoHeavyChild)`.
- **`Memo(Имя)` со звёздочкой в конце** — метку проставил уже Compiler. В коде нет ни `React.memo`, ни `useMemo` — он всё расставил сам на этапе сборки. Звёздочка нужна именно затем, чтобы не смешивать два источника мемоизации в голове студента: то, что явно в исходнике, и то, что добавлено автоматически.
- **Может быть сразу две метки `Memo` — и это нормально.** Положусь на то, что уже обсуждалось выше: Compiler не удаляет ваши ручные обёртки, он мемоизирует поверх них. Компонент, который вы сами обернули в `React.memo`, а затем Compiler доставил внутрь свои `useMemo`/`useCallback`, даёт сразу два слоя мемоизации. В DevTools это видно как два связанных значка `Memo` в дереве — один свидетель вашей ручной обёртки, другой такая же отметка Compiler'а у внутренних вычислений. Если двойная мемоизация не нужна — снимите `React.memo` руками: Compiler делает ту же работу сам, и звёздочка остаётся единственной меткой.

**В чём разница на демо.** Берём одну строку родителя «Рендерим родителя» и смотрим на два счётчика из `RenderBadge`: у `WithMemo` и у Compiler-списка они стоят, у `WithoutMemo` и у `NoMemoList` (с `"use no memo"`) растут. Если переключить `vite.config.js` на Babel-вариант и обновить страницу, DevTools покажет то же самое — разницы в поведении между вариантами быть не должно.

## Когда что применять

- Сначала снять замер: где ощущается тормоз? Нет измерений — нет `useMemo`.
- `React.memo` — на дорогих детей, у которых часто рендерится «лишний» родитель с другим состоянием.
- `useMemo` — только когда результат нужно передать дальше по ссылке, либо когда вычисление реально тяжёлое, вроде `.map → .filter → .reduce` на массиве из 10k.
- `useCallback` — только когда идёт в `React.memo` или в зависимости `useEffect`.
- Compiler включён — навязчивую привычку «обернуть всё в `useMemo`» можно отложить: авто‑мемоизацию он возьмёт на себя сам.
